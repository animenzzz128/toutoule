## What worked

- **Decisions made before the pressure arrived.** The cut list (D-007), the stopping rule for
  iteration (D-009) and the one-adjustment rule for scoring (D-010) were all written before the
  first result came in. When results disappointed, there was nothing left to negotiate, so
  nothing was tuned until it looked good.
- **The baseline made the claim honest.** Scoring a plain prompt on the same 50 postings
  (D-004) turned "low hallucination" into a measured difference: fabricated values fell from
  17 to 3–5 ([iteration log](../eval/iteration_log.md)). Without the baseline there would be
  nothing to compare against.
- **Code checks beat prompt edits.** v4's support check removed exactly the 4 `resume` claims
  its hypothesis predicted, with no API calls. The prompt-only versions (v2, v3) traded one
  error for another: v2 cut hallucination and raised false negatives, and v3 did the reverse.
  Prompt edits move along the trade-off; code checks move the trade-off itself.
- **Writing hypotheses down first.** The iteration log shows v1's prediction missing badly
  (14 vs ~5). That miss was more useful than a hit, because it surfaced misfiling as a second
  error type that the verbatim check cannot see.

## What didn't

- **Some targets were never plausible.** A 0% critical-hallucination target assumed that
  every error is a made-up value. 8 of v1's 14 errors were real quotes filed under the wrong
  field. I should have set targets per error type once v1 showed there were two.
- **The scoring miss was a specification error.** My 20 hand scores measured *priority*
  (city, company, interest in AI PM work). The system measured *résumé fit*
  ([scoring.md](../eval/scoring.md)). I asked myself an ambiguous question and the system an
  exact one. The rubric should have been written for the human rater first.
- **The label language was never tested.** Labels are in English, and a correct Chinese
  answer scores as a miss. That understates important accuracy and recall in every run. One
  bilingual test case before the first run would have caught it.
- **There is no held-out set.** Skipping it saved time before the ByteDance window, and it now
  limits how far any number can be trusted (D-009, D-010).
- **Assumed data turned out wrong.** The tracker's "13 manual Priority Scores" were 32 scores
  assigned by an AI (D-010). Market is never stored, so the tracker's Market column is
  always blank (D-011). Both were found late, when the plan reached them. Both could have
  been found by opening the data and tracing every output column back to a stored field
  before writing the plan.
- **An estimate in the PRD was never checked against its own measurement.** The PRD says
  manual triage takes 15–20 minutes per posting. The timing in
  [baseline.md](../eval/baseline.md) measured a median of 5 minutes for the field-finding part.
  The ≤ 3-minute target saves less than the PRD implies, and the next comparison (C5b) has to
  use the measured 5 minutes.
- **The rhythm stopped after Checkpoint D′.** There have been no commits since 10-11. The PRD
  predicted this risk ("build time displaces interview preparation"), and accepting it was
  right. The plan just never said what happens after the pause. D-014 is that plan.

## What I'd do differently

1. Before setting a numeric target, read a few early outputs and set targets per error type.
2. Write the rubric a human rater uses with the same dimensions the system scores, and
   collect the two scores separately.
3. Keep a held-out set from the start, even if it's only 10 postings.
4. Open every input file the plan depends on, and trace every output column to a stored
   field, before estimating.
5. Write the Friday retro anyway, even if it's three lines.
